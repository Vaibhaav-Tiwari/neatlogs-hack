# Human approval points

Tally keeps account access, data capture, repository changes, and paid work behind clear choices. A successful `tally doctor` check proves a connection is reachable; it does not approve Entire capture, CFO table creation, or a worker run. `tally doctor` checks that a coding CLI is signed in; it does not probe model access.

## Setup choices

### `tally init`

Review the final proposal before answering `Apply these changes?`. It shows the repository and base branch, tests and setup commands, models, budget, runner, integrations, and files/configuration to be written. This last confirmation writes `tally.yaml` and `.tally/install.json`; AO setup, when selected, also changes the named AO project settings. Setup and test commands execute repository code and can install dependencies.

The integration choices authorize the actions described in their prompt and summary. The following external actions still have their own consent or human review:

- **Neatlogs project key and worker hooks:** answering Yes to `Enable Neatlogs traces and machine-wide worker hooks?` authorizes a synthetic verification span and global hook installation for the selected agent(s). This changes the matching settings under your home directory and can trace matching sessions outside Tally. Tally backs up existing settings before writing them. The project key is stored in `~/.tally/.env` and does not grant history reads. Leave Neatlogs off if machine-wide session tracing is not intended.
- **Neatlogs history read:** if `NEATLOGS_TOKEN` is already present, init connects read-only history automatically after verifying `NEATLOGS_PROJECT_ID` or asking you to select a project. Use a project-scoped token with `context:read` and `observability:read`. Tally stores credentials outside the repository and reads through the Public API; it does not write history records through this reader. Without valid credentials it uses local history. See Neatlogs' [authentication and scopes](https://docs.neatlogs.com/api-reference/authentication) and [pagination contract](https://docs.neatlogs.com/api-reference/pagination).
- **Entire login and Graph plugin:** approving login starts Entire's own browser authentication; approving Graph installs its CLI plugin. These are account/machine changes and are independent of Tally's final config write.
- **Entire CLI installation:** if the Entire CLI is missing and Entire is selected, init offers its official platform installer and requires a separate yes. This installs only the CLI. Login, Graph installation, repository capture, hook trust, settings publication, and a repository mirror remain separate approvals. See [Entire's installation guide](https://docs.entire.io/installation).
- **Entire repository capture:** before enabling capture, review the proposed repository files and local Git hooks. A second confirmation is required before Tally commits only the listed settings and pushes them to the repository's default branch. That push is a GitHub write and can enable checkpoint/session evidence for future workers. Declining publication leaves capture unavailable to worker worktrees until you publish the settings through your normal review process.
- **Entire repository mirror:** this is a separate opt-in after capture setup. Confirm only if you want Entire to hold a copy of the GitHub repository. The Entire CLI asks which region or regions to use, and Tally verifies a mirror is ready before it adds browser session links to PRs. Declining keeps local checkpoint capture and normal runs available; hosted recall and hosted session links need a mirror. The selected region and copy are external Entire account changes.
- **Entire hooks:** after repository capture is published, open your coding agent's hook view, inspect the Entire hooks, and trust them for this repository. If you decline or have not trusted them, init keeps Entire disabled. Tally cannot approve hooks on your behalf.
- **cfo.ai login and selection:** approving connection starts cfo.ai's OAuth flow in a browser. Select the intended workspace and scenario; these determine which organization's monthly budget and spend tables Tally reads and updates.
- **cfo.ai table creation:** if required tables are missing, Tally displays their names, rows, formulas, and starting values, then asks before creating them. Existing tables and model data are not reset. Table creation is an external cfo.ai write.
- **cfo.ai Ari context:** answering Yes to `Use cfo.ai for budget, spend and Ari context?` adds or updates a Tally-managed guide on the selected scenario page and enables one operational report per attempt in organization-scoped cfo.ai memory. The guide is only updated when it has Tally's marker; other page blocks are left alone. Memory reports are shared with members of the selected workspace. They include task title/ID and issue link, repository, model/tier and configured rates, token usage when reported, estimated cost and its provenance, attempt ceiling/outcome/routing decision, budget snapshot, and PR/Entire/Neatlogs/cfo.ai links. Reports exclude issue bodies, source code and diffs, worker prompts and transcripts, raw trace contents, and credentials. Dry runs do not publish reports. The local ledger remains Tally's record; a failed memory write does not fail verified work and is reported in the run result.
- **Neatlogs and cfo.ai software setup:** Neatlogs tracing uses Tally's bundled SDK; cfo.ai uses built-in MCP OAuth. Neither needs a separate product CLI/package. Neatlogs key verification, the global hooks, and cfo.ai context/report setup follow their integration opt-ins as described above.

## Before each run

- `tally doctor` checks configured connections and agent sign-in. It does not start workers, test a model request, trust Entire hooks, create CFO tables, or publish repository settings.
- `neatlogs key: connected` means the ingest key is configured; it does not prove that `NEATLOGS_TOKEN` can read the selected project's history. In a plan, `History source: remote Neatlogs` confirms a matching remote observation. `local Neatlogs fallback` means Tally used local observations; if neither source has usable data, the plan shows `none` and may include a `History note`.
- `tally run --plan` reads the selected GitHub backlog, local repository signals, Neatlogs history when enabled, and CFO.ai budget/spend when enabled. It starts no coding agent, writes no CFO.ai spend, and creates no PR. Neatlogs history reads have a 15-second total deadline; if that read fails or times out, Tally reports the fallback and uses local history.
- `tally run --dry-run` uses simulated workers and does not make paid model calls or write simulated spend to CFO.ai. It is not offline: when Neatlogs is enabled, route-decision traces may still be sent remotely. Use `--plan` for a no-worker, read-only preflight; it reads enabled services but does not export decision traces.
- `tally demo --live` also uses simulated workers and does not write simulated CFO.ai spend, but it may export route-decision traces to Neatlogs when enabled. Treat that as a remote trace write, not a read-only demo.
- **`tally run` is the approval to perform real work.** It starts the configured coding agent, uses the model account, edits a worker worktree, runs the configured verification command, and can publish a PR after verification. With cfo.ai enabled, real usage is written to the selected spend tables; if a write fails, Tally keeps a local CSV fallback. Review the task list and effective available budget before starting.
- The run cap and CFO.ai monthly remainder are both applied. `--budget` only tightens the available amount. Spend monitoring depends on usage reported by the harness/provider; it is not a provider-side billing limit, so set a conservative cap and retain the provider's own billing controls.
- If CFO.ai cannot be read, a preview labels that it is using `tally.yaml`'s fallback. A real run configured with a cfo.ai budget may use its explicit local fallback when the service is unreachable; that run cannot enforce the live account remainder. Restore the cfo.ai connection before starting if the live budget is the required source of truth.

## What the current onboarding transcript still requires

If init says the Entire hooks are not trusted, review them in your coding agent's hooks view even when the hook files were created and pushed. If you skip it, Tally intentionally keeps Entire off. A config flag or `doctor` result cannot replace that human decision.
